# Security policy

## Reporting a vulnerability

Please report vulnerabilities privately through GitHub's **Report a vulnerability** button on the repository's Security tab. Do not open a public issue or pull request for a suspected vulnerability.

Include the affected version, a description of the impact and the steps to reproduce it. You will receive an acknowledgment, and a fix will be coordinated with you before public disclosure.

## Supported versions

Security fixes are released for the latest published version.

## Deployment model

Duckpad listens on `127.0.0.1` by default. An instance serves individual accounts with instance roles (member or administrator) and private projects with reader, operator, editor and administrator roles, which the server checks on every request.

- Protected API routes require a session or bearer API token. Login, first-launch setup and the single sign-on handshake are public. The first start prints the initial administrator password and a setup link once. The link's token stays in server memory: it works once, only while that generated password is unchanged, and never after a restart.
- `duckpad reset-password` gives a local account a new generated password from the server's command line and revokes its sessions. It requires access to the instance directory, which already holds the instance's secrets.
- Interactive accounts can create projects and administer the projects they create. Service accounts cannot create projects and are limited to Reader or Operator access.
- Connections and their secrets are stored in the instance directory, which is created with owner-only permissions. Keep that directory private. Secret connection parameters, the SSO client secret, assistant API keys and OAuth2 client secrets, and account SSH private keys are encrypted with a [master key](docs/INSTALLATION.md#secrets-and-the-master-key). By default, Duckpad generates that key in the instance directory, so a copy of the whole directory exposes the secrets; provide it with `DUCKPAD_MASTER_KEY_FILE` to keep it elsewhere. Encryption does not protect against someone who controls the Duckpad process or reads the key, and an instance administrator can point a connection at another host while keeping its saved password. Secret parameters can instead read [server secrets](docs/CONNECTORS.md#secrets-from-the-server), limited to `DUCKPAD_SECRET_*` variables and regular files directly in `DUCKPAD_SECRETS_DIR`, excluding the master key. Put only connection secrets there.
- By default, project SQL runs in isolated worker processes limited to the project's files and authorized connections. Connector definitions and DuckDB extensions are administrator-installed code that runs with the permissions of the Duckpad process. Only import projects, connectors and extensions that you trust.
- Granted database connections open the parent directories of their local `file` parameters in the selected environment, for reading and, with the connector's `write` capability, writing. Journals require directory access; all neighboring files and subdirectories become accessible to project SQL. Administrators should keep each database and environment in a dedicated directory. These directories must exist and exclude instance metadata, its parent directories and other projects, just like Server folder roots. Symlink targets are resolved before authorization and the kernel denies escapes outside the granted directories.
- Python execution is disabled by default and requires an instance administrator's per-project activation. Python uses the SQL worker's filesystem policy, with read-only project runtime libraries. It is not a hostile-code sandbox: network access and same-user process signals are deliberately unconfined. Enabling Python grants code access to the secrets of all authorized connections attached in the same worker; there is no separate secret-isolation switch. Dependency source builds require a separate administrator opt-in. Trust editors and dependencies; source builds run with the server account's permissions. See [Python nodes](docs/PYTHON.md) for resource and failure behavior.
- `duckpad start --trusted-local` disables OS filesystem isolation for a single trusted user, including on macOS and Windows. SQL and Python still run in a separate context worker, with the user's operating-system permissions; API permissions are not a filesystem boundary in this mode. Authentication and connection grants remain enabled. The CLI requires a loopback bind, and the option must be supplied on each launch. Do not use this mode for shared access or expose it through proxies, tunnels or port forwarding.
- Network Git never uses the SSH keys, agent, SSH or Git configuration, credential helper or Kerberos tickets of the server account. SSH origins use the key that Duckpad generated for the account that triggers the operation, only on hosts whose keys an instance administrator trusts, and only after that account confirmed the project's exact origin URL. HTTPS origins run without credentials and require an allowed URL prefix. The API never returns private keys, and deactivating an account deletes its key.
- What an account's key can read from a confirmed origin becomes visible to the project's members. Add a Duckpad key only to a Git host account whose repository access you accept to share with the projects where you confirm origins. The instance directory holds every account's private key; keep it private and back it up as a secret.
- With single sign-on, enable **Create member accounts on first SSO sign-in** only when every identity that your provider accepts for this client may use the instance.
- Before exposing Duckpad on a network, put it behind an HTTPS reverse proxy and set `DUCKPAD_SECURE_COOKIES=1`. When the proxy runs on another host or container, set `FORWARDED_ALLOW_IPS` to its address so that login throttling applies to each client instead of the proxy as a whole.
